WIC CoE · research project · ESP32 + Azure

A fleet of devices that repairs itself, and measures how fast it did

Small ESP32 boards report their own health every five seconds. When something breaks, the board tries to fix it first. If it can't, the cloud tries a ladder of fixes. If the cloud runs out of options, a person gets a message. Every step is timestamped, so the project produces real numbers on how fast each tier recovers.

Tier 1 · edgeThe device

First aid. Restarts a frozen task, frees leaked memory, reconnects WiFi, rolls back a bad update. Takes seconds.

Tier 2 · cloudAzure

The doctor. Sees the whole fleet, diagnoses per device, tries stronger fixes in order and checks each one.

Tier 3 · humanA person

The specialist. Gets a chat message only when automation gives up, or approves risky steps.

The problem

Devices fail in predictable, boring ways

IoT devices sit in farms, factories and buildings that nobody visits. They lose WiFi, a program freezes, memory slowly leaks, a bug floods the server with messages, a setting gets changed, or a firmware update breaks them. If a person has to notice and fix each one, recovery is slow and expensive.

Two numbers describe how well a system copes. MTTD (mean time to detect) is how long until something notices the failure. MTTR (mean time to recover) is how long until the device works again. This project is built to measure both, under controlled conditions.

Architecture

How the pieces talk to each other

All devices connect to Azure IoT Hub. Everything they send flows to the ingestion service, which stores it and watches for trouble. Problems become jobs for the remediation function, which sends commands back to the device through the same hub.

Tier 1 · the device

The edge healer: check, act, verify, report

The board has no sensors attached; it watches itself. Every five seconds it sends free memory, WiFi signal, uptime, reconnect counts, heal counts and its running settings. Once a second, the edge healer looks for four symptoms. When it finds one, it applies a fix, confirms the fix worked, and tells the cloud exactly what happened and when.

Symptom the board seesUnderlying faultEdge fix
App task stopped ticking for 5 sTask hangRestart the app task
Free memory below threshold, 3 checks in a rowMemory leakRestart the app task, which frees everything it owned
More than 5 messages per second for 3 sRunaway message loopRestart the app task
Running settings differ from the cloud's desired settingsConfig driftReapply the desired settings
WiFi or MQTT connection lostNetwork outageReconnect with exponential backoff (1, 2, 4, 8 s), reset the WiFi driver after repeated failures, buffer messages to flash and send them later
New firmware can't send telemetry within 60 sBad updateRoll back to the previous firmware (next section)

Edge healing can be switched off per device from the dashboard (it travels to the board through the device twin). With it off, the board behaves like simple tutorial code: it retries WiFi every 30 seconds, drops messages while offline, and trusts any firmware it's given. That's the baseline the experiment compares against.

Tier 1 · safe updates

Over-the-air updates with automatic rollback

The ESP32's flash holds two firmware slots. An update is downloaded into the empty slot while the old version stays untouched. After rebooting into the new version, the board has 60 seconds to prove it works by connecting and actually sending at least three telemetry messages.

Canary rollouts. The dashboard's Firmware page updates one board first (the canary), waits until it is healthy on the new version, then moves to the next. If any board rolls back or isn't healthy within four minutes, the rollout stops and the rest of the fleet keeps its current firmware.

Firmware files contain no passwords. Each board's WiFi and IoT Hub credentials are written once over USB and stored in its own memory, so one firmware file works for every board and can sit safely in cloud storage.

Tier 2 · the cloud

Detection, then the escalation ladder

The ingestion service watches each device separately and raises four kinds of detection. Each one fires once when the problem starts, not every five seconds while it continues.

telemetry_stale

No live telemetry for 30 seconds. Could be a frozen task, a bad update, or a device that's offline.

heap_low

Free memory under the device's threshold in two readings in a row.

message_flood

More than 30 messages in 10 seconds. Replayed (buffered) messages don't count.

config_drift

The settings the device reports differ from the settings Django wants, two readings in a row.

A detection becomes a job for the worker, which tries fixes from least to most disruptive. After every step it asks the device for its health and only moves on if the device still isn't healthy. This is the ladder for a silent device:

Safety rules

  • Yield to the edge. If the device reports it's mid-heal or mid-self-test, the cloud waits instead of interfering.
  • Check before every step. If another tier already fixed it, the ladder stops.
  • One ladder per incident. The worker claims the incident first, so duplicate detections do nothing.
  • Circuit breaker. Six or more cloud fixes on one device in 30 minutes means something deeper is wrong, so the cloud stops and calls a person instead of rebooting forever.

Three remediation modes

  • manual The cloud only detects and notifies. A person resolves it from the dashboard.
  • automated The cloud runs the whole ladder on its own.
  • approval Safe steps run automatically; reboot and rollback wait for a person to approve.
Incident lifecycle

What Django records for every failure

Each failure is an incident. Its state moves forward as tiers report in. The rule is first to verify wins: if the device already fixed it, the cloud can't later claim the credit.

Findings the design is set up to show

  • Edge healing recovers in seconds for problems the board can see in itself.
  • The cloud is slower but catches what the board can't judge alone, like a bad update when the self-test is off.
  • The cloud cannot fix the connection it depends on; network recovery always comes from the device or a person.
  • Approval mode adds human delay only to the risky steps.
  • Store-and-forward buffering keeps data loss near zero during outages.
Glossary

Terms used above

Edge computing
Doing work on the device instead of in the cloud.
Telemetry
Health and status data the device sends on a schedule.
Direct method
A remote function call from the cloud that the device answers, such as reboot.
Device twin
A JSON document in IoT Hub holding the settings the cloud wants and the settings the device reports.
OTA update
Installing new firmware over the network.
Rollback
Booting back into the previous, working firmware.
Canary rollout
Updating one device first as a test before the rest of the fleet.
Escalation ladder
Fixes tried in order of disruption, ending with a person.
Circuit breaker
Stop automatic retries after too many attempts in a short time.
Exponential backoff
Waiting 1, 2, 4, 8 seconds between retries.
Store-and-forward
Saving data locally while offline and sending it once reconnected.
Fault injection
Breaking things on purpose to test recovery (chaos engineering).
MTTD / MTTR
Mean time to detect / mean time to recover.
